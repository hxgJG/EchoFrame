# Lumio 应用发布与更新方案

本方案覆盖 GitHub 安装包发布、App 内检查与下载更新，以及 Android 和 macOS 的安装边界。从新的首个发布版本建立更新基线，不考虑此前测试版本的覆盖安装、签名迁移或数据迁移。首版采用独立公开发布仓库，不改变源码仓库可见性；macOS 暂无 Apple Developer Program 账号，先提供下载与手动安装，不实现自动覆盖。

首版不要求用户登录 GitHub，不自动安装，不强制更新，不做差分更新；不上传用户媒体、歌词、播放记录或设备安全码。

建议新发布基线使用 `1.0.0+1`，以后每次正式发布递增构建号。首版 Android 使用新生成的专用 Release 签名密钥，不再以 debug 密钥发布。新密钥首次安装不兼容同包名的旧 debug 签名 App；本方案不授权卸载、清空或重置当前设备的现有 App，安装冲突时应停止并由用户决定处理方式。

## 逐项问题与处理建议

| 问题 | 处理建议 | 边界或前置条件 |
| --- | --- | --- |
| 源码私密与免账号下载 | 使用独立公开发布仓库，Release 只附安装包、更新清单及说明，不复制源码 | 公开附件可被任何人下载；先确认仓库名和首批公开内容 |
| GitHub 上传与客户端下载 | 发布脚本使用开发端凭证上传草稿 Release，客户端通过 HTTPS 匿名读取公开附件 | 不在 App 中嵌入 GitHub token；没有账号系统也不需要自建业务服务 |
| Android 正式签名 | 为新发布基线生成专用 Release keystore，安全备份，所有后续版本沿用同一签名身份；缺少签名配置时发布构建直接失败 | 不使用 debug 回退，不考虑旧签名迁移；旧 App 安装冲突不自动处理 |
| 发布密钥管理 | Android 包签名密钥与更新清单签名密钥分开管理，保存于仓库外的受保护位置并备份 | 不把私钥、密码写入源码或日志；不要把设备互传身份密钥用于发布签名 |
| macOS 临时签名 | 首版下载 ZIP，校验后让用户手动替换 App；明确告知未公证与系统可能拦截 | 不移除隔离属性、不关闭系统保护、不声称临时签名等同正式签名 |
| macOS 自动更新 | 后续取得 Developer ID 证书、完成公证后再评估 Sparkle 与沙盒集成 | 首版不自动写入 `/Applications`，也不请求提权替换 |
| 发布版本管理 | 新基线建议从 `1.0.0+1` 开始，此后建立递增构建号；用户可见版本与构建号分别管理，清单按构建号判断新旧 | 不扫描旧测试包来确定新基线；已发布的新基线版本号与附件不可复用 |
| 下载内容损坏或被替换 | 使用签名的版本清单、SHA-256 和长度校验；Android 再验证包名、构建号和证书 | 哈希不是来源认证。客户端只内置验证公钥，不包含发布私钥 |
| GitHub 网络不稳定 | 流式下载、超时、取消、有限重试；失败保留当前可用 App | 首版不承诺断点续传；预留固定可信备用源接口，不接收任意下载地址 |
| API 限流 | 使用公开 Release 中固定命名的签名清单，常规检查不依赖 REST API；检查结果缓存 | 手动检查保留防抖，不能频繁重试；下载时处理 HTTPS 重定向 |
| 检查与下载影响播放 | 首版只手动检查更新，下载任务独立于播放状态；流式写入临时文件，哈希处理避免阻塞 UI | Android 安装前提醒播放将中断，macOS 提示先退出再替换 |
| 后续更新丢失数据或重置安全码 | 从新基线开始保持包名、bundle identifier 和存储路径，升级前写入当前会话，数据格式变更采用兼容迁移 | 保留新基线以后产生的音乐、视频、歌词、书签、偏好和设备身份；旧测试版本数据迁移不在范围内 |
| 发布了错误或不完整的包 | 先上传草稿并校验附件，全部验收后再公开；停止推荐有问题的版本 | 不覆盖同版本附件；回退发布采用更高构建号的修复包，不要求系统降级 |

Android 的签名要求见 [Android 应用签名](https://developer.android.com/studio/publish/app-signing)；macOS 正式分发要求见 [Apple 签名与公证](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)。

## 首版客户端交互

设置页增加“应用更新”，显示当前版本和构建号，提供“检查更新”。无网络或无更新时仅显示结果，不干扰离线播放。

发现新版本后，在 App 内展示版本、发布日期、更新说明、安装包大小与适配平台。用户点击下载后显示字节进度，可取消和重试；只在完整校验通过后提供安装操作。

- Android：点击“安装更新”后，按需打开系统的未知来源授权页，再进入系统安装确认。用户拒绝、返回或安装失败均不清空下载外的应用数据。通过安装权限校验后交给系统安装器，不实现静默安装。
- macOS：点击“显示安装包”后在 Finder 定位已下载 ZIP。说明解压、退出 Lumio、替换原应用、重新启动的步骤；用户自行处理系统确认。页面持续说明当前包未经过 Apple 公证，不承诺另一台 Mac 可以无提示运行。

首个发布版本通过手动下载安装，安装包内已包含更新模块和验证公钥；从这个版本开始，通过 App 下载后续更新。旧测试版本不接入本次更新链路。

## 发布包与版本清单

首版建议分别提供一个 Android 通用 APK 和一个经验证的 macOS 通用 ZIP，减少架构选择错误。后续可以按架构拆包，但清单和客户端必须提前具备平台及架构筛选字段。

发布内容包括：

- 带版本与构建号的 APK 和 ZIP，新基线建议命名为 `Lumio-1.0.0-1-android-universal.apk` 与 `Lumio-1.0.0-1-macos-universal.zip`，后续版本使用新版本和递增构建号。
- 固定命名的 `update-manifest.json` 及其分离签名 `update-manifest.sig`。
- 更新说明与安装提示，允许客户端直接展示，不通过网页执行更新逻辑。

清单字段至少包含 `schemaVersion`、`channel`、`version`、`buildNumber`、`publishedAt`、`notes` 和平台包列表。每个平台包包含平台、架构、最低系统版本、文件名、长度、SHA-256 与固定版本的下载 URL。

使用 Ed25519 等成熟签名实现，不自行编写密码算法。发布端签名原始清单字节，客户端验证同一份原始字节，验证通过后才解析。公钥内置客户端；私钥只保存在受保护的开发端或后续 CI secrets。清单签名与包的 SHA-256 提供来源和完整性检查，但不能替代 Android 平台签名、Apple Developer ID 或公证。

版本清单只引用固定版本附件，不使用会变动的 latest 链接作为安装包地址。签名文件与清单切换期间若不匹配，客户端停止本次更新，稍后重试，不跳过验证。清单、说明和包大小均设置上限。

## 发布流程与凭证管理

首版建议在当前 Mac 本地构建和发布，暂不引入 GitHub Actions 的远程签名。项目当前未安装 GitHub CLI；可在取得安装授权后配置 CLI，或使用浏览器手动发布，不需要把凭证写入项目。

1. 确定发布仓库、渠道与构建号，记录对应源码 commit。
2. 验证版本、签名、包名和目标架构，完成现有检查与覆盖升级验收。
3. 生成清单、哈希和清单签名，执行本地验签。
4. 创建草稿 Release 并上传附件；下载回读核对哈希、签名及包信息。
5. 全部附件通过后发布 Release；通过真实客户端验证发现、下载和安装。

上传需要发布端 GitHub 身份和仓库写入权限；当前没有读取或修改 GitHub 凭证，也没有创建发布仓库。上传安装包前检查日志、调试资源和配置，不公开任何媒体样本、用户状态、签名私钥或认证材料。

GitHub 官方提供 [Release 上传工具](https://cli.github.com/manual/gh_release_create) 和 [公开附件 API](https://docs.github.com/en/rest/releases/assets)。REST API 匿名请求按来源 IP 限流，见 [GitHub 限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。

## 实现模块与兼容边界

- Flutter：新增独立更新服务、签名清单解析、版本比较、下载状态及设置页入口，沿用已有平台桥接结构，不重构播放器。
- Android：新增限定范围的安装包缓存与分享 URI，安装权限检查、包身份检查及系统安装桥接；不要扩大现有媒体 FileProvider 的开放范围。
- macOS：新增安全下载路径与 Finder 定位桥接；不添加自动更新 helper，不修改当前钥匙串身份读取逻辑。
- 发布端：后续增加本地构建和发布前检查脚本，私钥与 GitHub 凭证均不提交仓库。
- 从新基线开始，应用升级时保持设备身份与安全码；未来进入正式 macOS 签名后，新基线用户的沙盒文件和钥匙串访问兼容性必须单独验收，不能只验证启动成功。

## 验收与上线顺序

1. 新发布基线准备：生成并备份专用 Android Release 密钥和清单签名密钥，确定新基线版本；不处理旧版兼容。
2. 客户端与本地发布校验：完成检查、验签、流式下载、取消重试和平台安装入口；使用测试清单验收，只发布新基线的 Release 签名 APK。
3. 发布仓库与真实下载：确认仓库名和附件后创建公开仓库，发布首个验收包，回读附件校验。
4. 真实升级：新基线先完成首次安装，再从该版本开始至少两次连续升级；验收更新后音乐、视频、歌词、历史、设置和设备安全码均保持，且播放可用。旧测试版不参与覆盖升级验收。

必须覆盖无网络、下载中断、磁盘不足、用户取消、错误平台、过低系统版本、无新版本、清单签名错误、包哈希错误、Android 不兼容证书、拒绝安装权限和安装失败。错误时不自动卸载、不清空数据、不跳过验证。

macOS 暂时仅验收下载与手动替换。未来自动更新另立阶段，在正式签名、公证和沙盒兼容验收通过后实施，不计入首版完成条件。

## 本地发布操作

在仓库根目录执行。`flutter`、`dart`、`gh` 需在 PATH 中；配置 `JAVA_HOME` 与 `ANDROID_SDK_ROOT`，签名配置默认读取仓库外 `.lumio-release/android-signing.properties`，可用 `LUMIO_RELEASE_CONFIG` 指定其他受保护的配置文件。

1. 首次密钥已生成，不重复运行 `tool/release_keys.dart`，不要为修复构建而重建密钥。先安全备份密钥目录。
2. 完成检查、验收并提交源码，保持工作区干净。调整 `pubspec.yaml` 的版本和构建号后构建 `flutter build apk --release`、`flutter build macos --release`。
3. 执行 `dart run tool/prepare_release.dart tool/release_notes/1.0.0.md`。该工具从干净提交重新构建两端，核对版本、正式证书、macOS 通用架构，生成带签名的附件于 `build/releases/v1.0.0-1/`，不覆盖既有发布目录。仅本地验收可加 `--local-preview`，复用当前构建；预览附件不能发布。
4. 开发端自行执行 `gh auth login`，不要向聊天或源码粘贴 token。取得仓库创建授权后创建独立公开仓库；建议在 GitHub 设置启用 Release 不可变保护。
5. 确认将公开的六个附件后执行 `dart run tool/publish_release.dart draft build/releases/v1.0.0-1`。工具不自动创建仓库、不覆盖既有版本、不上传其他文件。
6. 执行 `dart run tool/publish_release.dart verify build/releases/v1.0.0-1`，回读全部六个附件并逐一核对哈希、验签。回读副本保留于临时目录供检查。
7. 取得公开发布确认，执行 `dart run tool/publish_release.dart publish build/releases/v1.0.0-1`。该命令再次回读校验后才取消草稿状态，设为 latest。后续更新使用更高构建号与新的说明文件。

附件只包含 APK、macOS ZIP、`update-manifest.json`、`update-manifest.sig`、`RELEASE_NOTES.md` 与 `INSTALL.md`。安装包含应用程序及更新公钥，不含源码仓库、用户媒体、备份、设备身份或发布私钥。源码中的 UI 与逻辑可从公开二进制被分析，这与源码仓库是否公开是不同的边界。
