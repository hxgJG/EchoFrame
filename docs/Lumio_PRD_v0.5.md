# 忆光 Lumio —— 本地音视频播放器 App 需求文档

> 版本：v0.5
> 说明：本版本明确「离线优先」为核心设计原则（1.2、4 节），将在线封面/歌词独立为非核心的可选模块（新 3.7 节），并参考主流本地播放器（Poweramp/Musicolet/VLC/MX Player 等）补充了媒体管理、播放体验、系统集成方面的细节需求（新 3.6 节）。

---

## 1. 项目概述

### 1.1 背景
开发一款手机端本地音视频播放器 App「**忆光 Lumio**」，核心数据源为**用户手机本地存储的音频/视频文件**（非在线流媒体、无需账号体系）。音乐相关界面参考截图中的 Retro Music 风格；视频模块在交互逻辑和视觉语言上复用音乐模块的设计语言，降低开发与维护成本。

### 1.2 目标
- **离线优先（Offline-First）**：核心播放、媒体库浏览、播放列表管理等功能必须在完全无网络环境下 100% 可用；联网能力（封面/歌词在线补全）仅作为可选辅助，默认可一键关闭，关闭后不影响任何核心体验（详见 3.7）
- 提供流畅、美观、可自定义主题的本地媒体播放体验
- 音频与视频两类媒体共用一套设计体系，统一交互心智
- 技术架构具备跨平台扩展能力，覆盖 Android / iOS / HarmonyOS（鸿蒙），桌面端长期预留

### 1.3 已确认产品决策
| 编号 | 决策内容 |
|---|---|
| D1 | 目标平台：Android + iOS + HarmonyOS（鸿蒙）；桌面端（Windows/macOS）暂不考虑，仅作远期预留 |
| D2 | 数据源以本机文件导入/扫描为主（核心，必须离线可用）；在线获取专辑封面与歌词为**非核心的可选辅助能力**（详见 3.7、6.4），不含云同步、社交分享、多账号体系 |
| D3 | 音乐与视频在产品结构上是两个并列的"模式"（音乐库 / 视频库），通过顶层入口切换，各自拥有类似的二级导航（列表、详情、播放页） |
| D4 | iOS 导入方式确认为"用户主动导入"（而非全盘扫描），见 3.1 |
| D5 | 视频模式需要支持后台/小窗播放（PiP），见 3.3、6.4 |
| D6 | 不需要多用户 / 多媒体库切换，App 内媒体库为单一全局库 |
| D7 | 平台优先级：**首期集中力量做好 Android 端**，iOS 与 HarmonyOS 均可延后，不要求三端同步上线 |
| D8 | 在线封面/歌词功能定位为**可关闭的"增强功能"**，不投入商业授权数据源的预算，默认仍以本地嵌入信息优先 |
| D9 | 视频 PiP 在 HarmonyOS 上**后续再补**，鸿蒙首发版本可不支持 PiP |
| D10 | 字幕支持维持**二期可选**，不纳入近期范围 |

## 2. 产品结构与信息架构

```
App
├─ 音乐模式
│   ├─ 首页（推荐）
│   ├─ Songs（歌曲列表）
│   ├─ Albums（专辑）
│   ├─ Artists（艺术家）
│   ├─ Playlists（播放列表/播放队列）
│   └─ Now Playing（播放详情页：封面视图 / 歌词视图）
├─ 视频模式
│   ├─ Videos（视频列表，复用 Songs 的列表样式）
│   ├─ Folders（按文件夹浏览，可选）
│   └─ Now Playing（视频播放页，复用音乐播放页布局，封面区替换为视频画面）
├─ 搜索（独立页面，由首页、列表页、视频页顶部入口打开）
├─ 全局 Mini 播放器（音频模式下常驻，跨页面悬浮于底部导航之上）
└─ Settings（设置）
```

## 3. 功能需求

### 3.1 媒体导入与扫描（基础能力，音视频共用）
- **Android**：通过 `MediaStore` 全盘/指定目录扫描音频、视频文件；监听文件系统变化做增量更新；支持手动添加/排除文件夹
- **iOS（已确认：用户主动导入）**：iOS 无系统级公共媒体库，无法像 Android 一样"扫描全盘"。产品交互上采用用户通过文件选择器（Files / 文档选取）主动导入文件或授权文件夹访问，App 内维护一份"已导入媒体"的索引。需在 iOS 端设计专门的"导入"引导流程（区别于 Android 的自动扫描）
- **HarmonyOS**：鸿蒙有自己的媒体库 API（Media Library Kit），扫描方式与 Android 接近，但调用方式、权限模型、文件路径体系均不同，无法直接复用 Android 端代码，需要单独实现一套鸿蒙侧扫描逻辑（详见 6.4）
- 元数据提取：标题、艺术家、专辑、时长、封面图（音频 ID3/Vorbis/FLAC 标签；视频读取首帧缩略图、分辨率、码率、时长）
- 扫描结果落地本地数据库，做缓存与增量比对，避免每次启动全量扫描

### 3.2 音乐模式

**3.2.1 首页（推荐）**
- 顶部：搜索入口、Logo、设置入口
- 欢迎区：头像 + "Welcome, {用户名}"
- 快捷宫格（2×2）：History（历史）、Last added（最近添加）、Most played（最多播放）、Shuffle（随机播放全部）
- Suggestions 推荐区：大卡片（如"最近添加合集"）+ 缩略图网格 + 横向滚动的专辑/歌曲条目，基于本地播放历史/最近添加生成（非在线推荐算法）
- Recent artists：横向圆形头像列表 + 查看全部入口

> 封面/歌词的获取策略（本地优先 + 可选在线补全）已整体移至独立的 3.7 节，核心首页逻辑本身不依赖网络。

**3.2.2 列表页（Songs / Albums / Artists 共用模式）**
- Songs：纵向列表，缩略图 + 标题 + 艺术家 + 单条三点菜单（播放、加入队列、加入播放列表、详情、删除等）
- Albums / Artists：两列网格卡片，封面 + 标题 + 副标题
- 顶部搜索、排序/筛选（按名称、时长、添加时间、播放次数）
- 右下角悬浮按钮：一键随机播放当前列表

**3.2.3 播放列表（Playlists）**
- 创建/重命名/删除播放列表
- 列表内拖拽排序、批量添加/移除歌曲
- "播放队列"与"播放列表"概念区分（队列是当前播放序列的临时态，播放列表是持久化集合）

**3.2.4 播放详情页（Now Playing）**
- 两种视图，左右滑动或图标切换：
  - **封面视图**：大尺寸专辑封面居中
  - **歌词视图**：歌词同步滚动，当前行高亮加粗，前后行半透明渐隐；歌词来源按"本地 `.lrc` 文件 > 已缓存的历史在线结果 > 实时在线匹配"优先级获取（在线部分为可选辅助，详见 3.7），均无结果时留空并提示
- 进度条：当前时间 - 可拖拽滑块 - 总时长
- 歌名（大字）+ 艺术家名
- 主控制行：循环模式、上一曲、播放/暂停（视觉突出的圆角按钮）、下一曲、随机播放
- 底部工具行：收起、歌词/封面切换、收藏、查看队列、更多操作
- 下滑手势收起返回上一页，Mini 播放器无缝衔接当前播放状态

**3.2.5 全局 Mini 播放器**
- 跨音乐模式所有页面常驻于底部导航上方
- 显示封面缩略图、"歌名 • 艺术家"、播放/暂停按钮
- 点击展开为完整 Now Playing 页

**3.2.6 后台播放**
- 锁屏界面 / 通知栏媒体控制（播放/暂停/上下曲）
- 耳机/蓝牙设备的媒体按键响应
- 来电、其他音频打断时的焦点处理（暂停/恢复）

### 3.3 视频模式（复用音乐模式的设计语言）
- **视频列表**：样式同 Songs 列表，缩略图替换为视频帧截图，副标题展示时长/分辨率
- **视频播放页**：
  - 复用 Now Playing 的整体布局（进度条 + 控制行 + 底部工具行），封面区域替换为实际视频画面
  - 增加视频特有交互：全屏切换、手势调节（左侧上下滑动调亮度，右侧上下滑动调音量，水平滑动快进快退）、锁定屏幕方向
  - 退出播放页自动记忆播放进度，下次续播
- **后台/小窗播放（PiP，已确认需求）**：
  - Android：使用系统原生 PiP（`enterPictureInPictureMode` + Manifest 配置），切到后台或其他 App 时继续浮窗播放
  - iOS：使用 AVKit 原生 PiP（`AVPictureInPictureController`），该能力依赖画面通过 `AVPlayerLayer` 渲染，这会影响视频播放引擎的选型（见 6.4）
  - HarmonyOS：鸿蒙的悬浮窗/小窗能力与 Android、iOS 实现路径均不同，**已确认鸿蒙首发版本可不支持 PiP，后续再补**，不阻塞鸿蒙端的整体适配排期
- **字幕支持**（可选，二期）：本地 `.srt`/`.ass` 字幕文件匹配加载

### 3.4 搜索
- 全局搜索：歌曲/专辑/艺术家/视频统一入口，支持模糊匹配标题、艺术家名

### 3.5 设置模块
| 分类 | 说明 |
|---|---|
| Look and feel | 主题色、深色/浅色模式切换、动态取色（见 3.6.4） |
| Now playing | 自定义播放详情页布局（封面/歌词默认视图等） |
| Audio | 均衡器、Gapless/Crossfade、睡眠定时器、播放速度等（见 3.6.2） |
| Personalize | 播放控件样式、UI 细节个性化 |
| Images | 封面图来源与缓存策略（含 3.7 在线开关） |
| Notification | 通知栏样式自定义 |
| Other | 高级/实验性功能入口 |
| Backup & Restore | 播放列表、设置项的本地备份与恢复（导出/导入 JSON 或文件） |
| About | 版本信息、致谢、反馈入口 |

### 3.6 媒体管理与播放体验增强（参考主流本地播放器）

> 参考对象：Poweramp、Musicolet、BlackPlayer（音频）、VLC、MX Player、PotPlayer（视频）等主流本地播放器的常见能力，均为离线可用的细节增强，不依赖网络。

**3.6.1 浏览与媒体库管理**
- 双模式浏览：除按标签（歌曲/专辑/艺术家）的"媒体库模式"外，并行提供"文件夹浏览模式"，保留用户原始文件夹结构，照顾习惯按文件夹整理本地文件的用户
- 扫描范围控制：黑名单/白名单文件夹（如排除录音机、语音消息目录）、最短时长过滤（默认排除过短的音频文件，避免提示音/通知音被误收录）
- 多维度排序与视图：按名称、添加时间、播放次数、时长、文件大小排序；列表/网格视图切换
- 标签编辑器：App 内直接编辑标题/艺术家/专辑/封面（支持从相册选择或裁剪自定义封面），缓解本地文件元数据缺失或错误的问题
- 批量操作：多选模式下批量加入播放列表、批量删除、批量分享、批量重命名/移动文件
- 文件级操作：设为铃声/通知音/闹钟（Android 常见能力）、查看文件详情（路径、大小、编码格式）、调用系统分享

**3.6.2 音频播放体验**
- 无缝播放（Gapless）与淡入淡出切歌（Crossfade）
- 睡眠定时器：定时停止播放，支持渐弱淡出而非生硬切断
- 播放速度调节（如 0.5x–2.0x），对有声书/课程类本地音频友好
- 内置均衡器：多段 EQ + 常用预设（流行/摇滚/古典等）+ 自定义保存
- AB 循环 / 片段重复播放（常见于语言学习场景）
- 歌词偏移手动微调：解决部分本地 `.lrc` 文件轻微不同步的问题

**3.6.3 视频播放体验**
- 播放速度调节
- 画面比例/缩放模式（适应屏幕 / 拉伸 / 裁剪填充）
- 自动连播：按文件夹或播放列表顺序播放下一个视频（区别于"单个循环"）
- 字幕样式自定义（字号、颜色、位置），随二期字幕功能一并规划（D10）

**3.6.4 系统集成与个性化**
- 主屏幕 Widget 小组件：展示当前播放信息与基础控制按钮，无需打开 App
- 动态取色（Android 12+ Material You）：可选跟随系统壁纸取色，与现有浅色/深色主题体系并存，默认仍以参考截图的品牌蓝为主色
- 多语言：至少支持中文/英文界面切换
- 基础无障碍：兼容系统字体缩放、TalkBack 等屏幕阅读器的基本可用性

以上能力均为本地离线功能，不产生任何网络请求。

### 3.7 在线增强功能（非核心，默认可关闭）

> **设计原则**：联网能力仅作为锦上添花的辅助体验，**绝不能成为任何核心功能的前置依赖**。即便用户彻底关闭网络权限或本模块，App 的扫描、播放、媒体库管理、播放列表等核心功能必须保持 100% 可用，不弹错误、不卡顿、不降级体验。

- **范围**：仅限专辑封面与歌词的在线补全（对应 D2、D8 已确认决策），不包含其他任何联网功能
- **触发优先级**：本地嵌入信息 > 本地缓存的历史在线结果 > 实时在线匹配；命中本地即不发起网络请求
- **失败/无网处理**：静默降级为默认占位图、无歌词提示，不重试阻塞主流程，不弹错误提示打扰用户
- **用户控制**：设置中提供独立总开关"是否允许联网获取封面/歌词"，关闭后该模块在运行时完全不被调用，而非仅隐藏入口
- **架构隔离建议**：将该模块实现为独立可插拔组件（单独的 Service/Repository + 依赖注入开关），核心模块代码不直接依赖网络模块的任何类型或接口，便于完全裁剪、或在合规需要时整体下线而不影响主功能
- **数据源合规提示（持续有效）**：国内常见的"歌词/封面在线获取"多依赖第三方音乐平台的非官方接口，存在服务条款与版权风险，且接口随时可能失效；这不是法律建议，正式接入具体数据源前建议自行核实
- 不投入商业授权数据源预算（D8 已确认）

## 4. 非功能需求
- **性能**：千级以上媒体文件扫描不卡顿（异步扫描 + 分批入库），长列表滚动流畅（虚拟列表/懒加载）
- **格式兼容性**：
  - 音频：mp3、aac、flac、wav、ogg、m4a 等主流格式
  - 视频：mp4、mkv、mov、avi、webm 等主流容器/编码，需注意各播放引擎对小众编码的支持差异（见第 6 章）
- **权限适配**：Android 13+ 细分媒体权限（`READ_MEDIA_AUDIO`/`READ_MEDIA_VIDEO`）、Scoped Storage；iOS 文件访问权限与安全作用域 URL；HarmonyOS 媒体库相关权限模型
- **离线优先（核心原则）**：播放、本地媒体库浏览、3.6 节列出的所有管理与体验增强功能完全离线可用；仅 3.7 节的在线封面/歌词补全为可选辅助，默认可关闭，弱网/无网时优雅降级，绝不影响核心播放体验
- **网络请求治理**：3.7 节的封面/歌词请求需做频控与本地缓存，避免重复请求；用户媒体文件内容本身不上传，仅以歌曲名/艺术家等元数据发起查询
- **多主题**：浅色/深色完整适配（参考截图已提供两套配色基准）
- **跨平台一致性**：同一交互逻辑在 Android / iOS / HarmonyOS 上保持一致体验，差异仅体现在系统能力受限处（如导入方式、PiP 实现、后台播放机制）

## 5. UI/UX 设计要点（参考截图提炼）
- 卡片/按钮统一使用大圆角矩形，弱阴影或无阴影，扁平化风格
- 通用品牌交互使用紫—蓝—青色系；音频操作固定使用 Logo 音符的金橙色，视频操作固定使用 Logo 播放块的青绿色，深色模式提高两类语义色亮度
- 列表项缩略图统一圆角方形，标题加粗、副标题灰色弱化
- 悬浮操作按钮（FAB）用于"随机播放"等高频快捷操作
- Now Playing 页控制按钮中，播放/暂停按钮视觉权重最高（更大、纯色填充），其余为线性图标
- 歌词高亮采用"当前行清晰、前后行渐隐"的层次设计，营造沉浸感

## 6. 技术选型建议

### 6.1 方案对比

| 方案 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|
| **Flutter** | 单代码库覆盖 Android/iOS，自绘 UI 引擎，像素级还原参考截图的自定义样式容易实现；音视频生态在 Android/iOS 上已较成熟 | HarmonyOS 并非 Flutter 官方一等支持平台，而是依赖 OpenHarmony-SIG（社区，有华为/京东参与）维护的独立分支，与 Google 官方 Flutter 版本存在一定滞后；插件生态在鸿蒙上需要逐个验证或重新适配（详见 6.4） | **本项目推荐**，UI 高度自定义 + 需要覆盖 Android/iOS/HarmonyOS |
| React Native | 跨平台、生态大，RN-OH 鸿蒙适配也在推进中 | 自定义 UI/动画不如 Flutter 顺手，音视频播放插件成熟度普遍弱于 Flutter 生态 | 团队已有 RN 经验时可考虑 |
| 原生分端（Kotlin + Swift + ArkTS） | 性能与系统集成最优 | 三端独立开发与维护成本最高，与"统一设计体系、降低维护成本"的目标相悖 | 对性能/系统深度集成要求极高时 |
| Kotlin Multiplatform / 国产 KMP 方案（如 Kuikly） | 对鸿蒙 ArkUI、Ability 生命周期的官方化适配通常更深入、更贴近原生 | 生态与社区资源不如 Flutter 丰富，UI 自定义成本相对更高 | 若鸿蒙是产品的**首发或核心战场**而非"后续适配"，值得单独评估 |

**结论：综合"自定义 UI 还原度高 + Android/iOS 为主、HarmonyOS 为重要补充"的目标，Flutter 仍是当前最匹配的选择，但需要把 HarmonyOS 适配的工作量和风险单独评估、单独排期，不能假设它与 Android/iOS 同等成熟。**

### 6.2 Flutter 推荐技术栈（Android / iOS）

| 模块 | 推荐方案 | 说明 |
|---|---|---|
| 状态管理 | Riverpod 或 Bloc | 播放状态、列表状态较多，建议用可测试性强的方案 |
| 本地数据库 | Drift（SQLite）或 Isar | 存储媒体索引、播放列表、播放历史、封面/歌词缓存 |
| 音频播放引擎 | `just_audio` + `audio_service` | 业界验证较成熟的组合，`audio_service` 负责通知栏/锁屏控件与后台播放生命周期 |
| 视频播放引擎 | 官方 `video_player` + `chewie`（**优先**，因 PiP 需求） | PiP 在 iOS 上依赖 `AVPlayerLayer` 渲染路径，在 Android 上依赖系统 `enterPictureInPictureMode`，二者都更容易基于系统播放器（ExoPlayer / AVPlayer）封装的 `video_player` 实现；`media_kit`（基于 libmpv）编解码器覆盖面更广，对小众容器更友好，但走的是自绘渲染路径，不直接对接系统 PiP API，如需要可作为冷门格式的兼容性补充方案，而非默认主引擎 |
| 媒体库扫描 | Android：`on_audio_query`（音频）+ 自定义 MediaStore 查询（视频）；iOS：`file_picker` + 自管沙盒导入索引 | 两端扫描逻辑需分别实现，不能完全复用 |
| 元数据/封面提取 | `flutter_media_metadata` 或 `metadata_god` | 解析 ID3/Vorbis 标签与本地封面图 |
| 在线封面/歌词请求 | `dio`（网络请求）+ `cached_network_image` 或自建图片缓存层 | 配合 3.7 的优先级策略与请求频控；建议封装为独立可插拔模块；数据源需自行评估合规性 |
| 权限管理 | `permission_handler` | 处理 Android 13+ 细分媒体权限 |
| 歌词解析 | 自实现 LRC 解析 + 自绘滚动高亮组件 | 逻辑简单，自绘可完全还原参考截图效果 |

### 6.4 HarmonyOS 适配策略与风险评估

**6.4.1 现状判断**
- Google Flutter 官方目前没有原生支持 HarmonyOS，鸿蒙上的 Flutter 能力由 OpenHarmony-SIG 社区（华为、京东等参与）维护独立的 `flutter_flutter` / 引擎分支提供，需要使用专门的鸿蒙化 SDK 与 DevEco Studio 工具链开发，不能直接用官方 stable 渠道的 Flutter
- 已有部分官方插件被社区适配出"鸿蒙版"，例如音频方向已有 `just_audio_ohos` 这类适配库，相对成熟；但像 `video_player` 这种依赖系统播放器（ExoPlayer/AVPlayer）的插件，在鸿蒙上**没有现成官方替代**，需要团队基于鸿蒙自身的 Media Kit（AVPlayer/XComponent）自行实现一套平台桥接（MethodChannel + Texture 渲染绑定），工作量明显高于音频
- 常用基础插件（`shared_preferences`、`path_provider` 等）在鸿蒙上也需要替换为社区鸿蒙版或自行桥接，迁移成本会随项目依赖的插件数量增加而上升
- 工具链层面：暂无类似 Shorebird/Codemagic 的成熟热更新/CI 工具支持鸿蒙，打包与分阶段发布目前仍偏手动（DevEco Studio + HAP 打包 + 应用市场分发）

**6.4.2 对本项目的具体影响**
| 能力 | 风险等级 | 说明 |
|---|---|---|
| 媒体库扫描 | 中 | 需基于鸿蒙 Media Library Kit 单独实现，逻辑可参考 Android 方案但代码不可复用 |
| 音频播放 + 后台/锁屏控制 | 中低 | 已有社区适配方案可参考，相对其他能力风险较低，但仍需充分验证 |
| 视频播放 + PiP | 高 | `video_player` 无现成鸿蒙实现，需自行开发平台桥接；鸿蒙小窗/悬浮窗能力与 Android/iOS 的 PiP API 不通用，需单独设计交互与实现 |
| 在线封面/歌词请求 | 低 | 纯网络请求 + 本地缓存，跨平台逻辑可复用度较高 |

**6.4.3 落地建议**
- 架构上严格遵循"业务逻辑/UI 与平台能力解耦"：播放引擎、媒体库访问、后台控制等均通过抽象接口（Repository/Service 层）调用，具体实现按平台注入，确保某一平台插件不可用时只需替换实现，不影响上层代码
- 不要把 HarmonyOS 适配放进 MVP 阶段。建议先在 Android（+iOS）上完成核心架构与功能验证，再单独排一个"鸿蒙适配 spike"，重点验证音频后台播放、视频播放+PiP、媒体库扫描这三项高风险能力是否可行、工作量多大，再决定正式排期
- 关注 OpenHarmony-SIG 官方仓库与三方库适配状态（如 OpenHarmony 三方库汇总仓库），优先选用已有社区适配的插件，减少自研平台桥接的范围
