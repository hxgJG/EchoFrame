# 忆光 Lumio 功能状态矩阵

> 基线：`docs/Lumio_PRD_v0.5.md` v0.5
> 代码基线：`main` / `1.0.10（11）`
> 核对日期：2026-11-19
> 状态口径：✅ 已完成；🟡 部分完成；⬜ 未实现；⏸ 待确认或依赖外部条件

## 1. 当前结论

当前产品处于“Android 可发布 + macOS 可自更新 + HarmonyOS 可构建 spike + iOS 骨架”阶段。
Android 的媒体浏览、播放列表、音视频播放、搜索、续播、本地歌词/字幕、播放速度、
睡眠定时器、AB 循环、均衡器、自动 PiP、封面/首帧懒加载和批量分享等主链路已经可用；
1.0.10（11）起扫描结果统一以 MediaStore URI 播放，并在播放前校验媒体授权。
应用状态已按会话、媒体库、播放列表分区持久化，Android 使用 MMKV，HarmonyOS 使用系统
Preferences，macOS 使用应用支持目录下的分区 JSON，避免数据库和高频完整媒体库写入。
macOS 自 1.0.7（8）起保留 App Sandbox 并通过 Sparkle 应用内安装更新，但仍为临时签名、
未经 Apple 公证。iOS 仍是工程骨架；HarmonyOS 已有导入、播放和持久化桥接，并已完成
真机启动与首页渲染验证，但仍缺少完整播放回归与后台/锁屏能力。

## 4. 持久化技术决策

- 不引入 SQLite、Drift 等关系型数据库；当前数据以键值读取和整块媒体索引为主，没有复杂联表查询。
- Android 使用 `MMKV 1.3.9` 保存分区 JSON，利用 mmap 降低频繁小状态写入开销。
- HarmonyOS 使用系统 `Preferences` 保存相同分区协议，避免引入尚未在当前 Flutter OHOS 工程验证的第三方桥接。
- macOS 使用应用支持目录下的分区 JSON 文件；媒体来源授权以 security-scoped bookmark 单独保存。
- `session` 保存设置、队列和播放会话；`library` 保存低频媒体索引；`playlists` 独立保存。
- 常规设置/队列更新只序列化 `session`，不会再遍历全部媒体；媒体库只在扫描、收藏、
  播放统计、元数据或续播点变化时写入，视频续播写入间隔为 30 秒。
- 封面等二进制资源不进入 KV；当前使用内存缓存，后续如增加磁盘缓存则使用文件缓存目录。
- 只有出现复杂关联查询、局部索引更新无法满足性能且有基准数据证明时，才重新评估数据库。

## 8. 技术债与优化记录

### 8.1 2026-11-20 已优化

| 问题 | 影响 | 处理 |
|---|---|---|
| `audioItems` 每次访问都复制列表并全量排序，`videoItems`/`playlists` 每次访问都重建不可变副本 | 播放中每 700ms 重建一次界面，万级媒体库时每次重建约 2ms 全部消耗在重新排序上 | 按「源列表身份 + 排序方式」缓存；新增 `audioCount`/`videoCount`，只取数量的位置不再触发排序 |
| `albums`/`artists`/`audioFolders`/`recentlyAdded`/`mostPlayed` 每次访问全量扫描并排序 | 专辑网格在 `itemBuilder` 里取 `state.albums[index]`，每个格子都重算整份专辑集合 | 合并为 `_AudioIndex` 一次构建并按源列表身份缓存；专辑网格把聚合结果提到 `build` 外 |
| `queueItems` 每次访问都对全部媒体建索引表 | 播放列表页每次重建重复建表 | 按队列与媒体列表身份缓存 |
| `itemsForAlbum`/`itemsForArtist`/`itemsForAudioFolder` 每次调用全量扫描 | 专辑与艺术家网格每张卡片查询一次，全屏滚动退化为 O(卡片数 × 媒体数) | 在 `_AudioIndex` 中一并建立分组映射，结果转为不可变副本 |
| `_findItem`/`_itemsForIds`/`itemsForPlaylist` 每次都先拼出音频+视频全量列表再线性扫描 | 歌单页对每个歌单卡片查一次，50 个歌单 × 1 万条媒体时每次重建约 12ms | 建立按 id 的媒体索引并按源列表身份缓存，查找降为 O(1) |
| 搜索每次按键为全部媒体重新拼接并转小写检索文本 | 万级媒体库下每次按键约 1.9ms，输入有轻微延迟 | 建立按媒体库版本缓存的检索索引，只在媒体库变化时重建 |
| 缺少异步相关 lint | 存在「await 之后使用 BuildContext」和未显式处理的 Future 各一处 | 修复两处并启用 `use_build_context_synchronously`、`unawaited_futures` |
| UI 层直接用 `Platform.isX` 判断功能是否有入口 | 与 `PlatformCapabilities` 模型并存，新增平台时容易漏改 | 新增 `supportsPortableBackup`/`supportsDeviceTransfer`/`supportsAppUpdate`，设置页与应用更新页改读能力模型 |

实测（同一进程内对比，1 万条音频）：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 100 次界面重建读取全部派生视图 | 202 ms | 0.13 ms |
| 1000 次专辑卡片查询 | 90 ms | 0.11 ms |
| 100 轮 × 20 个歌单卡片查询 | 1187 ms | 3.1 ms |
| 10 次按键搜索 | 18.8 ms | 5.3 ms |
